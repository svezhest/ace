# Отклонения от апстримов

Каждое сознательное расхождение с апстримом (код оригинального репозитория на зафиксированном коммите) — с
причиной. Тесты-мостик (`tests/bridge/`) нормализуют только то, что записано здесь, и ссылаются на запись по её
идентификатору (`ACE2`, `SC1`, ...): CHK — проверки задач, ACE, DC, SC — SCOPE, EV — EvoLib, TF — TF-GRPO, MCE.

## Эталоны

Эталоны сняты с чистых HEAD апстримов на фейковой модели (`bridge/README.md`, `bridge/fixtures/`), тесты —
`uv run pytest tests/bridge`. Здесь — то, в чём наш код сознательно расходится с эталоном, и почему.

### Проверки задач

finer и formula — чекеры ACE (`eval/finance/data_processor.py`), meb — `eval_equation_balancer` DC; на эталонах
совпадают все строки (`tests/bridge/test_bridge_tasks.py`). Отчётная точность `accuracy` в summary — как
`evaluate_accuracy` ACE: у finer доля верных сущностей, у остальных доля вопросов; `correct` — число верных
вопросов целиком, как `answer_is_correct`, которым ACE судит попытки при обучении.

CHK1. **eval апстримов — только над арифметикой.** ACE (finer) и DC (meb) отдают ответ модели в `eval` целиком;
    мы вычисляем только строку из цифр, точки, `+ - * /`, скобок, `e`, `_` и пробелов, без `**` и без
    встроенных имён, иначе — как неудавшийся `eval` апстрима (сравнение строк у finer, неверно у meb). Причина:
    ответ модели — недоверенный код (`().__class__...`, `9**9**9` вешает процесс). Расходится только на
    `**` и именах встроенных функций; в ответах finer и meb их нет.
CHK2. **gpqa — наша проверка**: буква варианта в начале ответа. DC для GPQA-Diamond берёт
    `eval_for_multiple_choice` (засчитывает и текст варианта из вопроса: «Option B», «muon»); наша инструкция
    gpqa просит букву, и судим мы только её. Задача gpqa в стенде своя (выборка, формат), не из статьи DC.

### ACE

Эталон: ace 82709de (`bridge/fixtures/ace/`). `ace_exact` сверяется посимвольно: шаблоны и запросы рефлектора и
куратора, разбор их ответов (`extract_json_from_text`, `_extract_bullet_tags` без json_mode,
`_extract_and_validate_operations`), операции над playbook (id `calc-00001` со слагом `get_section_slug` и общим
номером, раздел general — в начало OTHERS, только ADD, метки — последняя на id, статистика, `extract_playbook_bullets`),
текст playbook, как его ведёт апстрим (пункт встаёт после пустой строки раздела), и цикл online на 4 задачах с тем же
фейком: все запросы рефлектора и куратора по порядку, итоговый playbook. Рефлектор и куратор отвечают текстом, как в
апстриме по умолчанию (`--json_mode` выключен), пустой системный промпт не отправляется.

ACE1. **Решатель общий для стенда**, не `GENERATOR_PROMPT`: системный промпт задачи, playbook в нём после «What you
    learned so far:» (пустой playbook не показывается), ответ строкой FINAL ANSWER, а не JSON с `final_answer`
    (`extract_answer` не нужен); вопрос — весь вход задачи (апстрим для formula вырезает вопрос и дописывает «Your
    answer should be a plain floating point number...»); траектория для рефлектора — наш транскрипт. Причина: методы
    сравниваются по памяти при одном решателе. Мостик подставляет в эталон нашу траекторию.
ACE2. **Какие пункты решатель использовал, он называет строкой USED, берутся все названные.** Апстрим по умолчанию
    (json_mode выключен) ищет id регуляркой `\[([a-z]{3,}-\d{5})\]` по тексту ответа (`generator.py:115`): она не
    видит `ph-` (слаг PROBLEM-SOLVING HEURISTICS из двух букв), верхний регистр и JSON-список `bullet_ids`, поэтому
    пункты этого раздела никогда не получают меток (в цикле эталона `ph-00002` остаётся 0/0). Мы ведём себя, как
    апстрим с json_mode: список как есть. Причина: регулярка — ошибка, которая молча выключает счётчики целого
    раздела; JSON-ответа у общего решателя нет. Мостик в цикле называет ровно те id, что вынула бы регулярка.
ACE3. **Онлайн: в зачёт — первая попытка обучения** (`pre_train_answer`). Апстрим сначала отвечает на окно из
    `online_eval_frequency` вопросов (по умолчанию 15) с playbook начала окна и засчитывает эти ответы, потом учится
    на каждом; ещё он прогоняет весь поток до обучения (initial test) и отвечает после куратора (только для
    отчёта). Мы этих генераций не делаем: это протокол стенда, один для всех методов, и он совпадает с апстримом
    при `--online_eval_frequency 1` и T = 0 (ответ окна и первая попытка обучения — один и тот же запрос).

### DC

Эталон: dynamic-cheatsheet 5cfe3c3 (`bridge/fixtures/dc/`).

DC1. **DC: решатель — общий решатель стенда.** Апстрим отдаёт решателю свой `generator_prompt.txt` (cheatsheet в
    блоке CHEATSHEET и вопрос в CURRENT INPUT одним сообщением пользователя), разбирает ответ `extract_answer`
    (`<answer>...</answer>`) и исполняет код по флагу «EXECUTE CODE!» в тексте ответа. У нас решатель один на все
    методы: системный промпт задачи, память после «What you learned so far:», ответ строкой FINAL ANSWER
    (`tasks.final_answer`), код — инструментом `run_python` (dc_code). Причина: методы сравниваются по памяти при
    одном решателе. Мостик сверяет, что решатель видит тот же текст памяти (то, что апстрим ставит в
    `[[CHEATSHEET]]`, включая "(empty)"), ту же температуру (0) и бюджет (max_tokens; куратор и синтез — вдвое).
DC2. **DC: вопрос для куратора и синтеза — контекст задачи**, без префикса задачи и «Question #k:», которые
    `run_benchmark.py` дописывает к `input_txt` (у MathEquationBalancer — инструкция задачи). Инструкция задачи
    у нас — часть промпта решателя (DC1), номер вопроса — артефакт прогона апстрима. Пары DC-RS и в апстриме
    хранят сырой вход датасета (`original_input_corpus`). Мостик заменяет `input_txt` апстрима сырым входом.
DC3. **DC: эмбеддинги BGE-M3 считаются на ходу**, а не берутся готовыми из `embeddings/<task>.csv` (для наших
    задач их у апстрима нет). Близость — скалярное произведение нормированных векторов, то же, что
    `cosine_similarity` апстрима; отбор top-k и порядок (самая похожая последней) — как в апстриме. Мостик
    подставляет векторы эталона.

### SCOPE

Эталон: SCOPE 4dc0da5 (`bridge/fixtures/scope/`). Совпадают: шаблоны, запросы синтезатора, селектора,
классификатора и оптимизатора, step_summary и get_strategic_rules_text, допуск 0.5, порог strategic 0.85 (в апстриме он и параметр оптимизатора, и зашит в strategic_store.py:201; при значении по умолчанию одно и то же),
лимит 20 принятых на агента без сброса между задачами, дубль по словам в своём домене, предел домена
(оптимизатор до int(0.8 · предела), затем усечение), номера правил оптимизатора между проходами, цикл эталона
на 7 задачах и второй прогон со strategic из первого. Модель отвечает текстом, разбор — функции апстрима
дословно (`parse.scope_*`: `_extract_json`, разбор анализатора, слияния, поглощения, конфликта и классификатора
со всеми откатами) и совпадает с эталоном на всех входах, включая JSON в прозе и одинарные кавычки. Журнал апстрима (history_store, prompt_updates/) — лог,
не память; у нас его роль — лог по вопросу.

SC1. **SCOPE: тип ошибки шага — по событию: ToolError, IncorrectAnswer, Truncated.** Апстрим пишет
    `type(error).__name__` исключения агента, repro/scope_run.py заворачивал неверный ответ в Exception
    («Error Type: Exception»). У нас исключений нет: ошибка инструмента — текст результата, неверный ответ и
    обрыв — события цикла; имя говорит модели, что случилось. Сообщение — как в repro.
SC2. **scope_bo2: кандидаты — одна модель дважды при T = 0.7**; в апстриме — основная модель и candidate_models,
    каждая по разу. Модель у стенда одна, разнообразие даёт температура. Селектор, отсев пустых и «no
    improvement needed», первый кандидат при сбое выбора — как в апстриме.
SC3. **SCOPE: поля агента для синтезатора — из задачи стенда.** agent_name — «<задача>_agent» (как repro),
    agent_role — системный промпт задачи (repro: строка роли), task — вопрос (repro: неизменное описание задачи;
    в апстриме — текущая задача агента). current_system_prompt — системный промпт решателя сейчас: роль задачи,
    подсказка среды, strategic при запуске попытки и tactical, принятые в этой попытке («## Learned Guideline:»),
    как промпт агента апстрима с применёнными правилами. repro дописывал правила всех прошлых задач в один растущий промпт; у нас tactical живут попытку
    (SCOPE сбрасывает их между задачами), поэтому его промпт длиннее нашего.

### EvoLib

Эталон: EvoLib 98266b2 (`bridge/fixtures/evolib/`). Промпты, разборщики (`parse.fenced`, `first_fenced`,
`subtasks` — дословно как `utils.py`), IG и Future IG, выборка из библиотеки (тот же поток `random`), слияния
insight и skill, `run_iteration` на 12 случаях и цикл в два прохода по 4 задачам с эталоном и без совпадают
с апстримом с учётом записей ниже.

EV1. **Промпты EvoLib без «math»** («You are an expert», «the following problem», «better problem solving»):
    наши задачи — финансы, gpqa, meb, а не только математика; остальное дословно (промпты варианта HMMT).
EV2. **Решатель — общий решатель стенда**, а не `HMMT_SOLVER_PROMPT`: системный промпт и инструкция задачи
    с форматом `FINAL ANSWER:`, просьба решать подзадачами (`evolib_subtasks.j2`, формат `<subtask>` из
    `HMMT_FORMAT_PROMPT`) — в системном промпте, раздел памяти с теми же вступлениями («Here are some subtask
    solutions ...», «Here are some insights ...») и строками — в конце системного промпта. Ответ попытки —
    строка `FINAL ANSWER:` (у апстрима — первый `<answer>` без `$`), решение попытки — вся траектория.
    Модель и её параметры — стенда (у апстрима o4-mini через reasoning API, EV6). Причина: одинаковый решатель
    у всех методов, сравниваются методы, а не форматы ответа. Мостик подставляет разбор `<answer>` апстрима
    вместо `FINAL ANSWER` и сверяет раздел памяти.
EV3. **Вариант с оценкой (evolib_judge) пишет в промпт insight вердикт лучшей попытки** («Evaluation: wrong»),
    как промпты кодовых задач апстрима пишут Test Result; у HMMT апстрим test_result в промпт не передаёт.
    Без вердикта модели неоткуда узнать, что лучшая попытка неверна (insight идёт только при неудаче).
    Метода «EvoLib с эталоном» в реестре нет; мостик сверяет ветку gold апстрима без этой строки.
EV4. **Вес skill снизу ограничен eps** (`skill_weight`). У апстрима пола нет, но IG и Future IG по построению
    не меньше нуля (лучший балл не меньше среднего), так что в достижимых состояниях вес тот же; пол
    защищает `random.choices` от отрицательного веса на искусственных входах.

EV5. **Сравнение решений идёт до слияния нового insight** (извлечение раньше памяти). В апстриме наоборот:
    `add_new_insight` до `is_better_solution`. Вызовы друг от друга не зависят, итог тот же; мостик сравнивает
    вызовы без учёта порядка.
EV6. **top_p 0.5 не передаём.** Апстрим зовёт всё при T = 0 и top_p 0.5 (решатель, insight, слияния,
    сравнение); при жадной выборке top_p не действует.
EV7. **В зачёт — ответ большинства на каждом проходе.** Апстрим в отчёт берёт сохранённое лучшее решение
    вопроса, которое меняется только при улучшении; на первом проходе (онлайн, epochs = 1) это одно и то же.

### TF-GRPO

Эталон: youtu-agent c2caa53 (`bridge/fixtures/tfgrpo/`). Совпадают посимвольно: все восемь шаблонов, запросы
сводки, преимущества, сверки и плана, разбор `<Experiences>` и ```` ```json ````, применение плана, таблица плана
(`_format_exp_and_ops`), фильтр групп, два батча `ExperienceUpdater.run` (опыты G0, G1, ...), показ опытов в
инструкции итогового агента, температуры и размеры из конфига (с учётом записей ниже).

TF1. **Цели агента и обучения — под задачи стенда** (`tfgrpo_objective_*.j2`, `tfgrpo_learning.j2`). У апстрима
    для math: «A math question that could falls into any areas of mathematics ...» и «... on math questions ...»;
    наши задачи — не математика, поэтому формулировки про задачу, форма та же: input / output и перевод строки в
    конце, как у yaml-блока апстрима (в его промптах перед закрывающим тегом цели пустая строка). Мостик подставляет цели, с которыми снят эталон.
TF2. **Траектория в сводке — транскрипт решателя стенда** (`render.transcript`), у апстрима — repr списка
    сообщений агента openai-agents (`json.loads(trajectories)[0]["trajectory"]`, jinja печатает питоновский
    список); инструкция агента до показа опытов — задача стенда, а не math_agent.yaml. Решатель общий для всех
    методов, формат сообщений чужого фреймворка не воспроизвести. Мостик кладёт строку апстрима в эпизод.
TF3. **Порядок вызовов обновления.** У апстрима по батчу: все сводки, все преимущества, все сверки, план. У нас
    сводки, преимущество и сверка идут по вопросу сразу после его группы (извлечение — масштаб вопроса), план —
    на батче. Библиотека до плана не меняется, поэтому промпты и ответы те же; мостик сравнивает вызовы по
    стадиям.
TF4. **Разобранный не-список пропускается, а не роняет обновление.** Сверка ответила JSON-объектом вместо
    списка: у апстрима объект доходит до `_batch_update`, `extend` кладёт в операции ключи-строки, и
    `_format_exp_and_ops` падает (`'str' object has no attribute 'get'`); у нас группа без операций. План-объект
    (или null, число) у апстрима тоже падение, у нас пустой план; элементы плана не-словари пропускаются (у
    апстрима — падение).
TF5. **Батч 20 из 40 задач** против 50 из 100 у апстрима (`batch_size`, `rollout_data_truncate`): те же 2 шага за
    эпоху при нашем размере выборки.
TF7. **Итоговый агент без опытов — T = 0.3.** У апстрима `_create_agent_config_with_experiences` возвращает
    температуру 0.3 только при непустой библиотеке, а `model_copy` в `build` поверхностный: при пустой
    библиотеке агент остался бы при 0.7. У нас попытка в зачёт всегда при 0.3 и top_p 0.95: без опытов это
    базовый агент апстрима (его оценка — при 0.3).

TF8. **val и тест гонят всю группу попыток**, в зачёт — попытка итогового агента (T = 0.3, top_p 0.95). У
    апстрима eval при обучении идёт тем же агентом, что rollout (T = 0.7, `training_free_grpo.py:81`, `:93`), на
    отдельном наборе и в отчёт не входит; отчёт — итоговый агент (Mean@32 — ожидаемая точность одной выборки). В
    онлайн-протоколе вопрос в зачёт решает одна выборка итогового агента с текущей библиотекой (Mean@1).

### MCE

Эталон: meta-context-engineering c4b7a7c (`bridge/fixtures/mce/`).

MCE1. **Без интерфейсов: режим апстрима «NO interface requirements».** У наших задач нет функций-интерфейсов:
    базовый агент получает промпт апстрима без сигнатур («No specific interfaces required», папки interfaces/ нет,
    валидации интерфейсов нет), мета-агент — «No specific interfaces defined»; остальной текст мета-агента
    дословный, включая упоминания интерфейсов (так апстрим говорит и при пустых сигнатурах). Решатель видит все
    файлы context/ в промпте — как наивный get_context, отдающий всё (апстрим: код интерфейса или агент,
    читающий context/, как symptom_diagnosis_agent). Задаче принадлежат: поле вопроса в data/train.json —
    `question` (у symptom_diagnosis — `symptoms`), одна метрика accuracy, ошибок программы нет (`train_errors` 0).
MCE2. **Без утилит: у базового агента только файловые инструменты.** Нет python, call_llm и эмбеддингов (наша
    песочница без сети). Из промптов убрано то, что о них: utils/ в дереве папки, раздел «Available Utilities»,
    раздел «Environment» (`uv run python`), у мета-агента пример Skill B (рефлексия через call_llm) и требование
    «Mention useful utilities». Остальное дословно.
MCE3. **Агенты SDK апстрима — наша модель с файловыми инструментами** (ls, read, create, append, edit, delete; ace/fs.py)
    вместо Read / Write / Edit / Glob / Grep / Bash; в просьбе дописать SKILL.md — «create tool» вместо «Write tool».
    Пути — от `/workspace` (как E2B-пути апстрима), относительные тоже годятся; системный промпт пустой, как у SDK
    по умолчанию; до 30 раундов инструментов. Мета-агент может писать во всю папку iter{k}_sub0 (апстрим —
    только в папку навыков, обработчиком прав), читать — всё в workspace, как апстрим. Если и после трёх просьб
    SKILL.md нет, апстрим падает (Meta-agent failed), у нас итерация идёт с навыком прошлой.
MCE4. **train в одном порядке на каждом проходе.** Апстрим на каждой итерации берёт train заново случайной выборкой
    с перемешиванием (`load_samples(random_sample=True, shuffle=True)`), поэтому состав батчей от итерации к
    итерации разный; у нас порядок протокола цикла один для всех офлайн-методов, батчи те же. id задачи в
    data/train.json — её место в проходе (у апстрима — строка файла).
MCE5. **Папка навыка — `.agent/skills/learning-context/SKILL.md`.** В апстриме `.claude/skills/...` — конвенция
    Claude Agent SDK, на котором написаны его агенты. У нас агентов SDK нет (MCE3), а папка с таким именем
    пересекалась бы с рабочими сессиями; в промптах мета-агента и базового агента путь заменён, остальное дословно.
