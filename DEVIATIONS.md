# Отклонения от апстримов

Сознательные расхождения с апстримами (код оригинального репозитория на зафиксированном коммите) — с причиной.
Всё, что воспроизводимо, — поведение апстрима по умолчанию; наши варианты — именованные ступени абляции в
docstring методов, не здесь. Тесты-мостик (`tests/bridge/`) нормализуют только то, что записано здесь, и
ссылаются на запись по идентификатору: S — общее для всех методов, CHK — проверки задач, дальше по апстримам.

Эталоны сняты с чистых HEAD апстримов на фейковой модели (`bridge/README.md`, `bridge/fixtures/`): ace 82709de,
dynamic-cheatsheet 5cfe3c3, SCOPE 4dc0da5, EvoLib 98266b2, youtu-agent c2caa53 (TF-GRPO), meta-context-engineering
c4b7a7c (MCE). Тесты — `uv run pytest tests/bridge`.

## Общее

S1. **Решатель общий для всех методов, кроме ace_exact, DC и TF-GRPO.** Методы сравниваются по памяти при одном решателе:
    системный промпт задачи, память — в нём же (после «What you learned so far:» или раздел метода), вопрос — весь
    вход задачи, ответ — строка FINAL ANSWER (`tasks.final_answer`), код — инструмент `run_python`, траектория для
    обучения — наш транскрипт (`render.transcript`). ace_exact идёт генератором апстрима целиком (`show/ace.py`:
    GENERATOR, свой решатель попытки `loop.Solver`); общий решатель с playbook — вариант ace_exact_used. Все
    варианты DC — генератором апстрима (`show/dc.py`: Generator — `generator_prompt.txt`, вход задачи как в
    `run_benchmark.py`, ответ `extract_answer`, у dc_code код по «EXECUTE CODE!»); TF-GRPO — агентом апстрима
    (`show/tfgrpo.py`: инструкции `math_agent.yaml`, инструмент execute_python_code, траектория — repr списка
    сообщений). Решатели апстримов:
    EvoLib — `HMMT_SOLVER_PROMPT` (ответ — первый `<answer>` без `$`; у нас просьба решать подзадачами в формате
    `HMMT_FORMAT_PROMPT` — в системном промпте, раздел памяти с теми же вступлениями — в его конце, решение
    попытки — вся траектория). Мостик подставляет в эталон нашу траекторию и разбор ответа и сверяет, что решатель
    видит тот же текст памяти.
S2. **Задачи стенда, а не бенчмарки апстримов.** Тексты апстримов, привязанные к домену их бенчмарка, заменены
    текстами наших задач, форма та же: цели агента и обучения TF-GRPO (`tfgrpo_objective_*.j2`,
    `tfgrpo_learning.j2` вместо math; input / output и перевод строки в конце, как у yaml-блока; у dapo — math
    дословно), инструкции агента TF-GRPO (у dapo — `math_agent.yaml` дословно, у остальных — системный промпт
    задачи, тот же текст про код и инструкция задачи вместо формата `<answer>\boxed{}`); промпты EvoLib
    без «math» («You are an expert», «the following problem», «better problem solving»); поля агента для
    синтезатора SCOPE — agent_name «<задача>_agent», agent_role — системный промпт задачи, task — вопрос,
    current_system_prompt — системный промпт решателя сейчас (роль, подсказка среды, strategic при запуске,
    tactical этой попытки); в data/train.json MCE поле вопроса — `question` (у symptom_diagnosis — `symptoms`),
    метрика одна — accuracy. Мостик подставляет тексты, с которыми
    снят эталон.
S3. **Протокол стенда один для всех методов.** (а) Онлайн в зачёт — первая попытка обучения. Исключение — ace_exact:
    протокол online апстрима (`learner.window`, `recheck`): начальный тест потока, в зачёт тест окна из
    `online_eval_frequency` (15) вопросов с playbook начала окна, после куратора ещё генерация (в лог). Офлайн ACE
    (начальный тест, val каждые `eval_steps` шагов) — общим офлайном стенда (val после прохода). (б) Train в одном
    порядке на каждом проходе: MCE на каждой итерации берёт train заново случайной выборкой с перемешиванием
    (`load_samples(random_sample=True, shuffle=True)`); id задачи в data/train.json — её место в проходе.
    (в) Размеры под наши выборки: батч TF-GRPO 20 из 40 задач (у апстрима 50 из 100 — те же 2 шага за эпоху), MCE
    40 батчами по 20 и val 10 (у апстрима 50 по 25 и 20). (г) TF-GRPO — протоколом апстрима (`learner.final`):
    проход по train только учит, в зачёт — тест итоговым агентом с библиотекой после обучения; тест — задачи
    стенда (у dapo — другие 40 задач DAPO), у апстрима AIME24; eval при обучении (`do_eval`, выключен) не
    воспроизводится. (д) EvoLib: в зачёт — ответ большинства на каждом проходе; апстрим в
    отчёт берёт сохранённое лучшее решение вопроса (при epochs = 1 одно и то же).
S4. **Модель одна, параметры запросов — стенда.** Все вызовы идут в одну модель стенда при T = 0 и общем пределе
    генерации (`model.params`, `config.MAX_TOKENS`), если метод не задаёт своё (TF-GRPO: агент при 0.3 / 0.7 и
    top_p 0.95 без предела генерации, обновление без параметров, как у апстрима; ace_exact: T = 0.0 и `max_completion_tokens` 4096, как
    `timed_llm_call` при api_provider openai; DC: T = 0.0 и `max_completion_tokens` 2048, у куратора и синтеза
    4096, как `_generate_openai`; вызовы SCOPE — без параметров, сообщение частями, как `create_openai_model` без
    temperature). У апстримов модели и параметры свои: EvoLib HMMT — o4-mini
    через reasoning API (`max_completion_tokens` 50000, `reasoning_effort` high; T = 0 и top_p 0.5 — только без
    reasoning API); scope_bo2 — основная модель и `candidate_models` по разу, у нас `candidate_models` — та же
    модель при T = 0.7 (селектор, отсев пустых и «no improvement needed», первый кандидат при сбое выбора —
    как у апстрима). Мостик сверяет параметры там, где эталон их пишет.

## Проверки задач

finer и formula — чекеры ACE (`eval/finance/data_processor.py`), meb — `eval_equation_balancer` DC; на эталонах
совпадают все строки (`tests/bridge/test_bridge_tasks.py`). Отчётная точность `accuracy` в summary — как
`evaluate_accuracy` ACE: у finer доля верных сущностей, у остальных доля вопросов; `correct` — число верных
вопросов целиком, как `answer_is_correct`, которым ACE судит попытки при обучении.

CHK1. **eval апстримов — только над арифметикой.** ACE (finer) и DC (meb) отдают ответ модели в `eval` целиком;
    мы вычисляем только строку из цифр, точки, `+ - * /`, скобок, `e`, `_` и пробелов, без `**` и без
    встроенных имён, иначе — как неудавшийся `eval` апстрима (сравнение строк у finer, неверно у meb). Причина:
    ответ модели — недоверенный код (`().__class__...`, `9**9**9` вешает процесс). Расходится только на
    `**` и именах встроенных функций; в ответах finer и meb их нет.
CHK2. **gpqa — наша проверка**: буква варианта в начале ответа. DC для GPQA-Diamond берёт
    `eval_for_multiple_choice` (засчитывает и текст варианта из вопроса: «Option B», «muon»); наша инструкция
    gpqa просит букву, и судим мы только её. Задача gpqa в стенде своя (выборка, формат), не из статьи DC.

## Методы

DC3. **DC: эмбеддинги BGE-M3 для задач без готовых эмбеддингов апстрима.** У meb — готовые, как в апстриме
    (строки `embeddings/MathEquationBalancer.csv` для наших вопросов: `data/meb_embeddings.csv`) и
    `cosine_similarity`; для finer, formula и gpqa их у апстрима нет — BGE-M3 считаются на ходу
    (`embed.similarity`), близость — скалярное произведение нормированных векторов. Отбор top-k и порядок (самая
    похожая последней) — как в апстриме.
DC4. **dc_code: код модели исполняется в песочнице стенда, а не `python3` хоста.** Апстрим
    (`utils/execute_code.py`) пишет код во временный файл и запускает его `python3` хоста с пределом 3 с; у нас —
    тот же файл в одноразовом контейнере без сети (`env/sandbox.py`: python 3.12 с numpy и sympy, `/tmp/code.py`,
    предел 3 с, stdout и stderr режутся до 20 + 20 строк и 64 КБ). Разбор блока, обёртка print и сообщения — как
    у апстрима (`show/dc.py`: run_block). Расходится: в traceback наш файл вместо случайного `/tmp/tmpXXXXXXXX.py`
    (у апстрима он невоспроизводим и сам), набор библиотек и версия python, очень длинный вывод. Причина: код
    модели — недоверенный. Запись живой модели снята с апстрима целиком в контейнере (`bridge/live/dc_code`);
    при её воспроизведении вывод исполнения берётся из записи, вывод песочницы на тех же блоках сверяется отдельно.
SC1. **SCOPE: тип ошибки шага — по событию: ToolError, IncorrectAnswer, Truncated.** Апстрим пишет
    `type(error).__name__` исключения агента. У нас исключений нет: ошибка инструмента — текст результата, неверный
    ответ и обрыв — события цикла; имя говорит модели, что случилось.
SC2. **SCOPE: агент и задачи — наши.** SCOPE — библиотека (`SCOPEOptimizer.on_step_complete`): агента, бенчмарка
    и чекера в апстриме нет. Агентный цикл вокруг неё — наша обвязка (S1: решатель, задачи и проверки стенда,
    run_python в песочнице), подключённая как в `examples/basic_usage.py`: strategic правила — в начале задачи,
    после каждого шага (вызов инструмента, итоговый ответ) — `on_step_complete`, принятое правило дописывается к
    системному промпту «## Learned Guideline:». Что агент сообщает о шаге (вывод, вызов, наблюдение, ошибка SC1),
    agent_name, agent_role и task (S2) — поля обвязки. Записи живой модели (`bridge/live/scope*`) сняты драйвером
    `bridge/live/scope/driver.py`: та же обвязка и библиотека SCOPE как есть; scope_k2 (перспективы из статьи, в
    библиотеке их нет) — два оптимизатора с разными synthesis_mode, у попытки k свой.
TF4. **TF-GRPO: разобранный не-список пропускается, а не роняет обновление.** Сверка ответила JSON-объектом вместо
    списка: у апстрима объект доходит до `_batch_update`, `extend` кладёт в операции ключи-строки, и
    `_format_exp_and_ops` падает (`'str' object has no attribute 'get'`); у нас группа без операций. План-объект
    (или null, число) у апстрима тоже падение, у нас пустой план; элементы плана не-словари пропускаются (у
    апстрима — падение).
TF9. **TF-GRPO: задачи группы и батча — по порядку.** Апстрим запускает rollout, сводки, преимущества и сверки
    через `asyncio.as_completed`, а тот раскладывает корутины в `set` по адресам (артефакт CPython): при
    concurrency 1 они идут в порядке адресов, от него зависят номера попыток в «Attempt i» и порядок операций.
    У нас — порядок списка; запись `bridge/live/tfgrpo` снята с `as_completed` в порядке создания задач
    (`sitecustomize.py`), как эталоны мостика.
TF10. **TF-GRPO: инструмент агента — ядро в песочнице.** Апстрим исполняет код модели IPython-ом в своём процессе
    (`python_executor`, env_mode local); у нас тот же код (`env/kernel.py`: разбор аргументов и ошибки как у
    FunctionTool openai-agents, `execute_python_code_sync`, str(dict)) в контейнере без сети на попытку, пакеты —
    numpy, sympy, scipy, ipython, matplotlib, pydantic версий апстрима (у апстрима в процессе все его пакеты).
    Расходится: workdir в выводе (случайный у обоих), после предела времени ядро начинается заново (у апстрима
    ячейка дорабатывает в потоке с тем же shell), параллельные вызовы одного ответа идут по очереди. Причина: код
    модели — недоверенный. Запись снята с апстрима целиком в контейнере; при воспроизведении вывод берётся из
    записи, вывод ядра на тех же вызовах сверяется отдельно.
MCE1. **MCE без интерфейсов: режим апстрима «NO interface requirements».** У наших задач нет функций-интерфейсов:
    базовый агент получает промпт апстрима без сигнатур («No specific interfaces required», папки interfaces/ нет,
    валидации интерфейсов нет), мета-агент — «No specific interfaces defined»; остальной текст мета-агента
    дословный, включая упоминания интерфейсов (так апстрим говорит и при пустых сигнатурах). Решатель видит все
    файлы context/ в промпте — как наивный get_context, отдающий всё (апстрим: код интерфейса или агент,
    читающий context/, как symptom_diagnosis_agent). Задаче принадлежат поля
    data/train.json (S2) и ошибок программы нет (`train_errors` 0).
MCE2. **MCE без утилит: у базового агента только файловые инструменты.** Нет python, call_llm и эмбеддингов (наша
    песочница без сети). Из промптов убрано то, что о них: utils/ в дереве папки, раздел «Available Utilities»,
    раздел «Environment» (`uv run python`), у мета-агента пример Skill B (рефлексия через call_llm) и требование
    «Mention useful utilities». Остальное дословно.
MCE3. **MCE: агенты SDK апстрима — наша модель с файловыми инструментами** (ls, read, create, append, edit, delete; ace/fs.py)
    вместо Read / Write / Edit / Glob / Grep / Bash; в просьбе дописать SKILL.md — «create tool» вместо «Write tool».
    Пути — от `/workspace` (как E2B-пути апстрима), относительные тоже годятся; системный промпт пустой, как у SDK
    по умолчанию; до 30 раундов инструментов. Мета-агент может писать во всю папку iter{k}_sub0 (апстрим —
    только в папку навыков, обработчиком прав), читать — всё в workspace, как апстрим. Если и после трёх просьб
    SKILL.md нет, апстрим падает (Meta-agent failed), у нас итерация идёт с навыком прошлой.
MCE5. **MCE: папка навыка — `.agent/skills/learning-context/SKILL.md`.** В апстриме `.claude/skills/...` — конвенция
    Claude Agent SDK, на котором написаны его агенты. У нас агентов SDK нет (MCE3), а папка с таким именем
    пересекалась бы с рабочими сессиями; в промптах мета-агента и базового агента путь заменён, остальное дословно.
