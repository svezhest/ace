# Отклонения

Каждое расхождение нового кода со старым (тег `pre-rewrite`) и с апстримами — с причиной. Тесты-мостик
(`tests/bridge/`) нормализуют только то, что записано здесь, и ссылаются на запись по её идентификатору
(`D14`, `B4`, `ACE2`, ...): D — новый код против старого, B — SCOPE, MCE, обёртки и гибриды, дальше —
расхождения с апстримами, найденные мостиком, по апстриму (ACE, DC, SC — SCOPE, EV — EvoLib, TF — TF-GRPO,
MCE).

## Регрессия промптов: новый код против старого

Проверка: `uv run python tools/trace.py /tmp/t.json && uv run python tools/compare.py tools/ref_variants.json /tmp/t.json`.
Эталоны: `tools/ref_trace.json` — 25 методов старого кода; `tools/ref_variants.json` — варианты ACE старого
кода под новыми именами (`tools/ref_variants.py`): новый `ace` = старый `swap(ace, curate=curate_json)`,
`ace_text` = `swap(ace, curate=curate_json, reflect=reflect_text)`, `ace_rewrite` = `swap(ace, curate=curate_rewrite)`.

| метод | итог |
|---|---|
| baseline | совпадает с `ref_trace.json` и `ref_variants.json` |
| ace_exact, ace_exact_dedup | расходятся с первого вызова рефлектора (D22): ответ текстом, а не по схеме; фиктивная модель называет `USED: r1, r2`, которых нет в playbook, и рефлектор получает строку апстрима «referenced ... none were found» |
| ace, ace_text | совпадают с `ref_variants.json` |
| ace_rewrite | расходится (D1): с 4-го вызова память — пункт на строку с новыми id, дальше фиктивная модель отвечает иначе (ответ — хэш промпта) |
| ace против `ref_trace.json` | расходится с первого вызова куратора (D3) |
| dc, dc_code, dc_rs, dc_retrieval, dc_history | совпадают с `ref_trace.json` (память сравнивается по видам: у нового кода пары и cheatsheet в разных контейнерах, D13) |
| evolib | расходится с 20-го вызова (D17): лучшая попытка другая; с подменой ответа первой попытки, как в старом решателе (`tools/as_old.py`), совпадает |
| evolib_judge | расходится порядком: судья после каждой попытки (D7); с судьёй после группы и подменой (`tools/as_old.py`) совпадает |
| tfgrpo | расходится с первого вызова: попытка в зачёт при T = 0.3, top_p 0.95 (D14), дальше фиктивная модель отвечает иначе; с настройками старого кода (`tools/as_old.py`: жадная T = 0 в зачёт, метки опытов — id, группа без top_p, обновление при T = 0, цели без перевода строки в конце — TF6) совпадает |

## Методы

D1. **ace_rewrite: перезапись памяти — новые записи, по одной на строку.** Было: ответ куратора целиком —
   одна запись; если в памяти ровно одна запись, куратор правил её текст, сохраняя id и счётчики (`[r1]`
   во всех промптах); иначе старые удалялись. Стало: все старые пункты уходят со статистикой, каждая
   непустая строка ответа — новый пункт с новым id и нулевыми счётчиками. Причины: статистика принадлежит
   неизменяемому тексту, правка текста — новая запись (REVIEW.md, «Уроки и файлы»); промпт куратора просит
   «one bullet per line», а одна запись на всю память делала метки рефлектора бессмысленными (одна метка
   на всё).
D2. **Куратор стенда: UPDATE — новый пункт.** Было: UPDATE менял текст пункта, id и счётчики оставались.
   Стало: новый пункт на месте старого, новый id, счётчики с нуля. Причина та же. Фиктивная модель UPDATE
   не выдаёт, трасса не видит.
D3. **База цепочки `ace` — куратор операциями одной схемой**, а не агент с файловыми инструментами над
   пунктами со счётчиками. Причина: файловый куратор над записями со статистикой — запрещённая смесь двух
   миров памяти (REVIEW.md, «Решено: вариант 1»). Файловый куратор над уроками убран совсем.
D4. **ace_text: память без счётчиков и отсева.** Свободный текст меток не даёт, а память со счётчиками их
   требует — стык не соберётся. Раньше счётчики были, но в них ничего не приходило, отсев не срабатывал:
   поведение то же.
D5. **ace_exact_dedup: слитый пункт — новая запись** с новым id на месте первого (было: id первого).
   Счётчики — как вернула модель (сумма по группе), как в апстриме (BulletpointAnalyzer). Промпт слияния
   по-прежнему просит id первого — он нужен только для разбора ответа. Фиктивная модель слияний не даёт.

D22. **ace_exact приведён к апстриму по мостику** (`tests/bridge/test_bridge_ace.py`). Было: рефлектор и куратор
    отвечали по схеме (`Diagnosis`, `Curation`), урок куратору — пересериализованный диагноз, id пунктов `r1`,
    playbook разделами через пустую строку, метки одного id суммировались, в bullets_used — только найденные id в
    порядке USED, Question Context — весь вопрос. Стало, как у апстрима: ответ текстом и разбор его функциями
    (`parse.ace_json`, `parse.bullet_tags`, `parse.ace_operations`), урок — весь ответ рефлектора, id
    `calc-00001` (слаг раздела и общий номер), текст playbook апстрима, последняя метка на id, строки апстрима,
    когда id нет или они не найдены, пункты в порядке playbook, Question Context — `context` DataProcessor (у
    formula и finer в наших данных пусто), ошибка в любой операции куратора — ответ пропускается целиком.
D13. **DC: id и порядок записей в memory.json.** Было: все виды в одном списке с общей нумерацией (пара `r1`,
    cheatsheet `r2`, пары `r3`...). Стало: пары DC-RS — свой контейнер (`r1`, `r2`, ...), cheatsheet —
    документ с id `sheet`, в memory.json после пар. Тексты те же; id пар видны только в логе (`shown`).
    Синтезированный cheatsheet DC-RS память берёт из промпта попытки (`SheetPrompt.sheet`), а не из
    показанного текста эпизода (`context`): показ память не меняет. Поведение то же, включая откат на пары,
    когда синтез без блока `<cheatsheet>`.
D14. **TF-GRPO: в зачёт — итоговый агент апстрима, T = 0.3, top_p 0.95** (было: жадная попытка при T = 0).
    В апстриме температур три: rollout при обучении 0.7 (`training_free_grpo.py:84`), eval во время обучения
    делит с ними агента и тоже идёт при 0.7 (`:81`, `:93`), итоговый агент с опытами — 0.3 и top_p 0.95
    (`:248`, `configs/agents/practice/math_agent.yaml`). Отчётная метрика статьи — итоговый агент (Mean@32 —
    ожидаемая точность одной его выборки); eval при обучении идёт на отдельном наборе и в отчёт не входит;
    жадной T = 0 в апстриме нет вовсе. В онлайн-протоколе вопрос в зачёт решает агент с текущей библиотекой —
    одна выборка итогового агента (Mean@1). Группа из 5 при 0.7 — только для обучения, в зачёт не идёт.
    На val и тесте цикл гонит всю группу (D6), считается попытка итогового агента.
D15. **TF-GRPO: опыты помечены местом — G0, G1, ...** (было: id записей `r1`, `r2`). Так апстрим раздаёт
    ключи после каждого батча (`experience_updater.py:70`), эти метки видят решатель, сверка и план батча.
    Память переводит метки в свои id: UPDATE — новый опыт на том же месте (метка та же, как в апстриме), id
    памяти модели не видны и не адресуются.
D16. **TF-GRPO: план батча строится всегда, когда в батче были вопросы**, даже без операций («No batch
    operations.»), как в апстриме (`_batch_update` на каждом шаге). Было: без операций плана не было. В трассе
    не видно (у фиктивной модели операции есть в каждом батче). Элементы плана не-словари пропускаются (в
    апстриме и в старом коде — падение).
D17. **EvoLib: балл попытки — по её собственному ответу**, как в апстриме (`run_iteration`: `ans ==
    majority_answer` по списку ответов попыток). Было: старый решатель с `vote=True` подменял ответ первой
    попытки ответом большинства до вердикта, поэтому её балл всегда 1 и лучшая всегда первая; IG занижался
    (ответы x, y, y давали 0 вместо log 1.5 ≈ 0.41), лучшее решение и skills брались не из той попытки.
D18. **EvoLib: сравнение решений идёт до слияния нового insight** (извлечение раньше памяти). В апстриме
    наоборот: `add_new_insight` до `is_better_solution`. Вызовы друг от друга не зависят, итог тот же;
    мостику — нормализовать порядок.
D19. **EvoLib: старое лучшее решение сверяется с ответом большинства проверкой задачи** (`task.check`, как
    `eval_function` апстрима); было строковое `!=`. В трассе не видно.
D20. **EvoLib: top_p 0.5 не передаём.** Апстрим зовёт всё при T = 0 и top_p 0.5 (решатель, insight,
    слияния, сравнение); при жадной выборке top_p не действует.
D21. **EvoLib: в зачёт — ответ большинства на каждом проходе.** Апстрим в отчёт берёт сохранённое лучшее
    решение вопроса, которое меняется только при улучшении; на первом проходе (онлайн, epochs = 1) это одно
    и то же. memory.json: skill и insight с журналом `outcomes` (fig) и `ig`, doc у skill; лучшие решения —
    вид `best` с вопросом, ответом и баллом.

## Цикл и протокол

D6. **val оценивает всю группу попыток** с выбором в зачёт, как тест (было: одна попытка при T=0). Причина:
   val и тест меряют одно и то же. У портированных методов попытка одна — без разницы.
D7. **Вердикт попытки ставится сразу после попытки** (было: после всех попыток группы). Причина: масштабы не
   смешиваются, `on_attempt` видит вердикт. Для `judge` меняется порядок вызовов: у evolib_judge судья
   идёт между попытками.
D8. **Самоотчёт USED разбирает извлечение ACE**, а строку USED в системный промпт ставит показ ace_exact
   (было: сигнал `usage="self"` в цикле). Поведение то же. В логе поля `reported` больше нет; прочитанное
   инструментами — `read`, как раньше.
D9. **Срок жизни «задача» ушёл из цикла** (`memory.new_task()`): записи, живущие попытку или вопрос
   (tactical SCOPE), сбрасывает сам метод.
D10. **Шаговый режим модели** включается, когда у ученика показ смотрит шаги (`watches_steps`) и есть
    инструменты (было: событие шага обновления или хук инжекта). Для ACE и baseline шагов нет.
D11. **memory.json**: `kind` — имя контейнера (`bullet`), у ace_exact есть `section`; у уроков — журнал
    исходов `outcomes` и счётчики helpful / harmful. Скрытых видов больше нет: что решателю не видно —
    поле метода, а не вид памяти.
D12. **Лог по вопросу** дополнен группой попыток (ответы, вердикты, температуры, показанное, прочитанное,
    `fired`, `Patch`-и), способом выбора ответа (`pick`, `pass_at_k`), вердиктом группы (`vote`); `gated` —
    решения Gate на этом вопросе, а не последнее за прогон.

B3. **SCOPE: Patch системного промпта — только на шаге, где принято правило** (исходный промпт + все tactical).
    Раньше тот же текст ставился после каждого шага; промпт модели от этого не меняется, лог чище.
B4. **SCOPE: домены strategic в порядке появления**, как словарь апстрима (get_strategic_rules_text); раньше домен
    с новым правилом уходил в конец. Порог 0.85 — одна константа: в апстриме он и параметр оптимизатора, и

B5. **Оптимизатор правил (SCOPE, ace_opt): нетронутое правило остаётся той же записью** (id, счётчики пункта ACE);
    исправленные и слитые — новые записи со счётчиками с нуля. Раньше все записи группы пересоздавались с
    новыми id (поля переносились). Трасса до предела не доходит.
B6. **MCE: нулевой итерации нет.** Апстрим по умолчанию начинает с iter1 (`--start-iter 1`, mce/main.py:423), iter0 в

B7. **MCE: в evaluations мета-агента только итерации с первой** (iter0 в evaluations.json не пишется,

    aggregate_iteration_results), было — точность последнего батча.
B8. **Хуки: урок после ошибки — сообщением в конец истории** (Patch(append)), префикс цел; было — дописывание к

B9. **Хуки: тот же trigger с другим текстом — новая запись** со своим id и счётчиками с нуля (было: тот же id).
    У хуков свои id (h1, h2, ...), чтобы не путаться с записями ученика в показе.
B10. **ace_opt: предел с оптимизатором заменяет отсев вредных**, как в старом коде (замена bound); метки
    по-прежнему идут в счётчики.
B11. **ace_bo2: кандидаты рефлектора при T=0.7**, как у scope_bo2 (BEST_OF_TEMPERATURE); в старом коде T=0, и
    два кандидата выходили почти одинаковыми — выбирать было не из чего.

## Мостик к апстримам

Эталоны сняты с чистых HEAD апстримов на фейковой модели (`bridge/README.md`, `bridge/fixtures/`), тесты —
`uv run pytest tests/bridge`. Здесь — то, в чём наш код сознательно расходится с эталоном, и почему.

### Проверки задач

finer и formula — чекеры ACE (`eval/finance/data_processor.py`), meb — `eval_equation_balancer` DC; на эталонах
совпадают все строки (`tests/bridge/test_bridge_tasks.py`). Отчётная точность `accuracy` в summary — как
`evaluate_accuracy` ACE: у finer доля верных сущностей, у остальных доля вопросов; `correct` — число верных
вопросов целиком, как `answer_is_correct`, которым ACE судит попытки при обучении.

CHK1. **eval апстримов — только над арифметикой.** ACE (finer) и DC (meb) отдают ответ модели в `eval` целиком;
    мы вычисляем только строку из цифр, точки, `+ - * /`, скобок, `e`, `_` и пробелов, без `**` и без
    встроенных имён, иначе — как неудавшийся `eval` апстрима (сравнение строк у finer, неверно у meb). Причина:
    ответ модели — недоверенный код (`().__class__...`, `9**9**9` вешает процесс). Расходится только на
    `**` и именах встроенных функций; в ответах finer и meb их нет.
CHK2. **gpqa — наша проверка**: буква варианта в начале ответа. DC для GPQA-Diamond берёт
    `eval_for_multiple_choice` (засчитывает и текст варианта из вопроса: «Option B», «muon»); наша инструкция
    gpqa просит букву, и судим мы только её. Задача gpqa в стенде своя (выборка, формат), не из статьи DC.

### ACE

Эталон: ace 82709de (`bridge/fixtures/ace/`). `ace_exact` сверяется посимвольно: шаблоны и запросы рефлектора и
куратора, разбор их ответов (`extract_json_from_text`, `_extract_bullet_tags` без json_mode,
`_extract_and_validate_operations`), операции над playbook (id `calc-00001` со слагом `get_section_slug` и общим
номером, раздел general — в начало OTHERS, только ADD, метки — последняя на id, статистика, `extract_playbook_bullets`),
текст playbook, как его ведёт апстрим (пункт встаёт после пустой строки раздела), и цикл online на 4 задачах с тем же
фейком: все запросы рефлектора и куратора по порядку, итоговый playbook. Рефлектор и куратор отвечают текстом, как в
апстриме по умолчанию (`--json_mode` выключен), пустой системный промпт не отправляется.
