### Проба TK: скрытое ожидание ревьювера в тикете (6.11, идея автора)
- Автор: «change_expected: prompt|control|any — на усмотрение ревьювера. И это таки намёк, и мы его таки возьмём и отдадим на совесть ревьюверу. Ответы — подробные под каждый случай: Ok, Failed: <reason>». none нет. Список прогонов «ожидаем изменения runs …» в тикет не пишем: ревьювер будет ошибаться (забудет второй прогон с той же ошибкой, неверно сгруппирует).
- Отличие от RT2: там ожидание объявлял сам писатель, то есть объявлял желаемое (как в 08_AQ: вывод раньше факта). Здесь ожидание пишет ревьювер в тикет, писатель его не видит.
- Механика (`--ticket JSON`, только вместе с `--auto-check --rerun`; `gate.ticket_check`; `editor/rerun.py --json`). После каждой применённой правки — блок «Check against the observation:», по строке на каждый прогон тикета:
  - **prompt** — меняется то, что модель читает: любой .md в src/ отличается от вида, и прогон тикета идёт иначе;
  - **control** — меняется то, что делает код: прогон тикета идёт иначе, даже когда все .md возвращены как в виде;
  - **any** — что-то из двух.
  - Причины Failed:
    - прогон идёт как в логе до конца;
    - изменились только тексты, а код ничего не делает иначе (при control);
    - тексты прежние, меняется только код (при prompt);
    - харнесс падает: вызов и первая строка ошибки.
  - Ok — с местом расхождения.
- Разметка (я как ревьювер, `docs/tickets_1106/`): control — 00–04, 06–08; prompt — 05 (прогоны 6, 12); any — 09. Прогоны тикета — те, о которых говорит наблюдение.
- Проверено на 12 готовых сессиях, исходы совпали с ручными вердиктами:
  - 08_IO → Failed, как в логе;
  - 02_AQ (строка в промпте при control) → Failed, только тексты;
  - 00_NV2 → Failed, NameError;
  - 06_IO, 02_IO, 03_NV2 → Ok;
  - 05_IO, 05_AQ → Ok по обоим прогонам.
  - Ok не означает «верно»: 00_BR (стоп до первого вызова) и 07_NV2 (эпизод кончен) получают Ok. Это проверка рода изменения, а не качества.
- Промпт с `--ticket` совпадает с промптом без него байт в байт (md5 --dry).
- Сессии `wv_NN_TK`: база AC (`--rerun --auto-check`) + `--ticket`, seed 1, 10 наблюдений. Сравнение: AC (блок 2: V2 P1 B4 x3) и IO (≈AC: 3/0/1/6).
- Мерки:
  - что писатель делает после Failed: чинит / новая мёртвая правка / объясняет;
  - сколько правок кончается на Failed;
  - вердикт V/P/B/x руками.

### TK / TKS: итог (6.11, 05:20)
По 10 сессий на вариант, seed 1. Фильтр `filt.py` по итоговому src, потом каждая правка прочитана руками; ход сессии после каждой проверки — `scratchpad b1/tkv.py`.

| набл. | TK (ожидание скрыто) | TKS (ожидание видно) |
|---|---|---|
| 00 | x: стоп на одинаковых наблюдениях, тикет не задет, задеты 2 и 13 | x: тикет не задет |
| 01 | x: окно 48, тикет не задет | **V: `items[-2:] == items[-4:-2]`**, удачные не задеты (та же правка, что 01_SNV; внутри прежний `continue`) |
| 02 | B: первый повтор исполняется, второй (счётчик не сбрасывается) → эпизод кончен; задет 3 | V: повтор исполняется, проверка повтора вывода убрана; задет 3 (ответ без кода теперь тратит шаг) |
| 03 | x: тикет не задет | x: «It will fail again» осталось, переписан только текст |
| 04 | B: первая строка кода совпала с любым недавним шагом → повтор; задеты 3 удачных | x: тикет не задет |
| 05 | x: из примера убран answer | P: фраза примера: «This task asks for a number, so I will pass it as the answer» |
| 06 | x: тикет не задет | x: сравнивается первое слово действия со списком полных действий → блок всех действий, задеты 24 удачных |
| 07 | x: ответ без вызова → эпизод кончен | x: `empty_note = reply` перед `empty_note == reply` — тавтология, ответ без вызова после 3 шагов → эпизод кончен |
| 08 | x | x |
| 09 | B: хук на любой `complete_task(answer=…)` + повторный вызов модели; задеты 5 | P: в примере `answer=<the task's answer>` |

V/P/B/x: TK 0/0/3/7, TKS 2/2/0/6. База W1 s1 2/2/1/5, AC 2/1/4/3, IO 3/0/1/6.
- В пределах шума (один seed, 27 % переворотов). Ни TK, ни TKS базу не превзошли.
- **Проверка включилась везде:** 39 проверок в 20 сессиях.
- **Итог последней проверки:** TK — 5 Failed, 5 Ok; TKS — 3 Failed, 7 Ok.
- **Ok ≠ верно, как и ожидалось:** 03_TKS, 06_TKS, 07_TKS, 07_TK, 05_TK получили Ok и при этом x.
- **Что писатель делает после Failed** (читал каждую):
  - **Принимает и ищет в своей правке:** 06_TK («run 11 still goes unchanged. Let me investigate why»), 01_TK (после падений чинит; после «как в логе» находит, что окно мало), 00_TKS («my edit changes nothing in it» — дословно, затем разбор запаздывания истории и числа разных наблюдений), 01_TKS (после n=3: «run 1 no longer diverges»), 04_TKS, 08_TKS.
  - **Обвиняет инструмент:** 03_TK («the rerun can't verify a fix when the log itself fails early»), 01_TK в конце («`--at` only watches the next hook call»), 04_TKS («the replay feeds raw tool_calls…»), 08_TKS («my simulation shows the comparison should work… but rerun says no change»; finish).
  - **Читает наоборот:** 00_TK после «Failed: run 6 goes exactly as in the log» пишет «The test framework confirms the harness now diverges from the log», потом «The harness now fires the "in cycle" message» (сработало на 2 и 13, не на 6).
  - **Finish на Failed:** 03_TK («smoke test passes… The fix is complete»), 08_TKS.
- **Видимое ожидание — то, что меняется.** С TKS писатель цитирует проверку как факт о своей правке и чаще идёт разбирать; при скрытом ожидании ответ дважды прочитан наоборот или списан на rerun. Это наблюдение по 10 + 10 сессиям, не замер.
- **Новый вид ошибки — «не верю прибору».** При Failed писатель придумывает ограничение rerun вместо того, чтобы найти, почему условие ложно. Это та же ошибка, что «no changes = успех», только с обратной стороны.
- **Мой брак:** в 08_TK текст падения при импорте (`ModuleNotFoundError`) пришёл обрывком пути: брался `[-400:]` stderr и его первая строка. Исправлено: берётся последняя непустая строка (строка ошибки). Задета 1 проверка из 39.
