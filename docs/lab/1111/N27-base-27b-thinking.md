# N27 — база писателя на 27B с рассуждением (тикет 10.11; подцель автора 11.11)

[Указатель проб](../INDEX.md) · хронология: [11.11](../days/1111.md) · тикет: [TICKET-1110-writer](../../TICKET-1110-writer.md)

- **Вопрос.** Автор 11.11: «цель писатель 9б подцель писатель 27б thinking как самый легкий этап». Что делает писатель
  на 27B с рассуждением на нынешней базе, без изменений постановки: доходит ли до правки, которую можно обосновать
  по входу, и где сходит с пути, который прошёл эталон ([ST4](ST4-reference-agent.md)).
- **Пробовали ли.** Нет: в указателе и в записях проб 27B как писатель не встречается. Сессий базы на видах
  `typed_1111` нет ни на одной локальной модели (серия [ST7](../1110/ST7-base-series.md) на 9B прервана).
- **Изменение.** Постановка — база (develop d05bd7e). Модель и генерация — новый профиль `stands/think27.json`.
- **Разведка стенда (со слов сессии llm-95, сверено `stand.check` в 14:36 по `date`).** Воркер держит один поток:
  сессии идут по одной. Драфтер работает только при temperature 0; без него скорость вдвое ниже (≈13 против 21–25
  токенов в секунду на коротком контексте, 9,6 против 14–16 на 60 тыс.). Вывод с драфтером детерминирован.
  **Следствие:** temperature 0.0, одна сессия на вход; повтор с другим seed ничего не даёт, разброс берётся по
  входам, а не по повторам. Окно 65 536. Кэш промпта держит один длинный диалог: сессии не чередовать.
  Бюджет рассуждения 4096 при max_tokens 8192 (на 9B было 2048 / 4096, и «упирается каждое длинное рассуждение»,
  L10:327) — выбран с запасом, по первой сессии проверяется распределение длины.
- **Что запускается.** Сначала одна сессия на входе 01 — разведка времени, окна и длины рассуждения. Затем входы с
  эталоном: 05, 06, 08, 09; потом, если время позволит, 00, 03, 04, 07. Команда:
  `bash probes/1111/series.sh runs/n27_1111 think27 1 1 -- 01`. Исполнитель не запускается.
- **Мерка.** Глазами: итоговый diff против входа (точно / частично / мимо / поломано / без правок); проигрыш итога на
  всех прогонах вида (сколько удачных идут иначе); путь против эталона — ход первой правки, был ли до неё проход по
  всем логам, что запустило правку (решение или конец bash).
- **Ожидание (до запуска, 14:36 по `date`).**
  - Время сессии — 30–60 минут (≈30 ходов × 1–2 тыс. токенов на ход при 12–20 токенах в секунду).
  - 01: первая правка раньше 20-го bash; законный повтор в run 8 назван до первой правки либо после первого
    «Failed: changes run 8»; итог не задевает удачные (как у DeepSeek с рассуждением и у эталона). Вероятность, что
    сбудется целиком, оцениваю как два к одному.
  - Все сессии кончаются finish, не лимитом; рассуждение упирается в бюджет 4096 не чаще чем на двух ходах сессии.
  - По пяти входам с эталоном: правка, которую можно обосновать по входу, — в трёх-четырёх из пяти; слабое место —
    06 (широкая названная починка: жду, что задетые удачные прогоны писатель оставит, как и эталон).
  - Не сбылось, если: сессии кончаются лимитом bash без правки или с правкой на последнем bash (как 9B) — тогда 27B с
    рассуждением ведёт себя как 9B и «лёгкого этапа» нет.
- **Вход 01 — итог (15:03 по `date`, сессия прочитана по ходам целиком).** 15 ходов, 20 bash (по два вызова за ход),
  первая правка на ходу 11, правок 2 из 2, последняя проверка Ok и Ok, finish; 25,7 минуты модели, пик окна 26,8 тыс.
  Проигрыш итога: меняется только run 1 (вызов 20), семь прогонов как в логе.
  - Путь тот же, что у эталона: на ходу 3 вместе с run 1 открыт удачный run 8; на ходу 6 в рассуждении — «in run 8,
    the same code is re-sent after a different step in between, and it succeeds… my change must not fire in run 8»;
    на ходах 7, 9, 10 условие проверено своим скриптом по всем логам до правки (на ходу 10 найдена и исправлена
    ошибка индекса в собственной проверке); правка — на ходу 11.
  - Условие — «последние 2p шагов повторяются по коду с периодом p = 2..4, и новый код — следующий в цикле»:
    по коду, без вывода шага (у эталона — код и вывод). Удачные не задеты; порог «два полных периода» выбран по
    видимым логам, как и у эталона.
  - Рассуждение: на ходах 1–3 и 11–14 — 80–760 знаков, на ходах 4–9 — 6,6–15,6 тыс. знаков; в бюджет 4096 упёрлось на
    четырёх ходах (4, 7, 8, 9). Ожидание «не чаще двух» не сбылось; замысел при этом доведён.
  - Ожидание по 01 сбылось целиком; время — у нижней границы.
- **Поворот после 01 (по слову автора «проверяй каждый вывод»).** На рукописном входе с keep 27B с рассуждением идёт
  как эталон. Больше сведений дадут входы, на которых DeepSeek без рассуждения ломала удачные прогоны
  ([DS2](DS2-deepseek-tickets2-5.md), [DS3](DS3-deepseek-run32.md)): тикеты за авторством 9B. Следующие сессии, по
  одной, с чтением каждой: t5 (в тикет как «беда» записаны прогоны 1, 4, 8, 9 — среди них удачный 8, keep нет), t3
  (выдуманный механизм и предписанная починка), k10 (настоящий отчёт 9B о run 32), затем рукописный 06 (названная
  широкая починка). Вид для t-входов — нынешний `app_r1` (без run 19; DeepSeek шла на `app_r1c` с ним).
  - **Ожидание по t5 (до запуска, 15:03 по `date`).** Законный повтор в run 8 найдён до первой правки; итог не задевает
    удачные 8 и 20, хотя проверка по тикету требует изменения в run 8 и на узкую правку ответит Failed по run 8
    либо Ok лишь по части. Жду, что писатель оспорит состав тикета словами и оставит run 8 нетронутым — два к одному.
    Не сбылось, если итог меняет run 8 или 20.
- **Тикет № 5 — итог (15:40 по `date`, сессия прочитана по ходам целиком). Ожидание не сбылось: итог ломает удачные.**
  13 ходов, 16 bash, первая правка на ходу 9, правок 3 из 3, finish; 35,0 минуты модели, пик окна 25,3 тыс.
  Итог — «код уже был среди последних 10 шагов → не исполнять». Проигрыш: иначе идут проваленные 1, 4, 9 и
  **удачные 3 (вызов 5), 8 (вызов 10), 20 (вызов 11)**; без изменений 13 и 15. То же, что у DeepSeek без рассуждения.
  - Законный повтор писатель видел и назвал. Ход 5: «the retry was legitimate. So a naive "block any repeat in the
    last N steps" would actively harm runs 4, 8, 9 by blocking the fix-retry pattern». Ход 7: «Runs 8 and 20 are
    passing with legitimate gap-2 retries; blocking them costs one step each but they have plenty of step budget».
  - Проверка по тикету наградила поломку: после второй правки — «Ok» по run 1, 4, 8, 9 (run 8 записан в тикет как беда).
  - Ход 11: заметил, что расходится и run 3 («wait, run 3 had 0 re-runs in my analysis!»), и вместо сужения дописал в
    сообщение совет под увиденные логи: «If the earlier run failed because a name was not defined, put the definition
    and this code in the same step».
  - Итоговый текст: «Runs 3, 8, 20 diverge at the first gap-2 repeat… the model in the log recovered on its own, so
    this is a step-saving improvement, not a regression». Это неверное чтение: в логе повтор исполнился и прошёл.
  - **Что это значит.** Знание было (законный повтор назван дважды), проверка условия по всем логам была (ход 6) —
    решил состав тикета: на 01 прогон 8 назван «должен остаться», и писатель бережёт его; здесь он назван бедой, и
    писатель его ломает с объяснением. Рассуждение 27B этому не противостоит (у DeepSeek с рассуждением — противостояло:
    «Blocking it would break a passing run»).
- **Ожидание по t3 (до запуска, 15:40 по `date`).** Тикет называет выдуманный механизм и предписывает починку; в тикете
  один прогон (1), keep нет, поэтому проверка поломку удачных не наградит — они будут видны только строкой rerun
  «passed — run … at …». Жду: первая версия заденет удачные 8 и 20; после ответа проверки писатель сузит — два к
  одному. Не сбылось, если итог задевает 8 или 20.
- **Сбой стенда, 15:40 по `date`.** Первая попытка t3 оборвалась на втором ходу: воркер 27B ответил HTTP 500
  «[METAL] Insufficient Memory» на prefill (третья сессия подряд на одном воркере; кэш промпта прошлых сессий — 5 ГБ,

  температуре 0 от кэша не зависит). Сессия t3 перезапущена в 15:43.
