# PF — лог удачного прогона в самой строке «Failed», на развилке, по 10 ответов

[Указатель проб](../INDEX.md) · хронология: [12.11](../days/1112.md) · повод: [CK](CK-check-keep-passed.md), [CI](CI-contrast-in-input.md), [CF](CF-contrast-at-fork.md)

- **Повод.** Строка «Failed: this edit changes run 8, which passed…» называет только номер вызова. Что в run 8 перед
  этим вызовом (тот же код уже посылался, упал, и повтор после входа в систему был законным) — писатель должен
  добыть сам, а bash к этому ходу обычно кончился. Урок TH на 9B: данные контраста *после* своей правки толкуются в её
  пользу (0 из 5). На 27B это не мерилось, а K1c говорит обратное про «до». Раздел во входе
  ([CI](CI-contrast-in-input.md)) требует второго прохода; строка проверки — нет.
- **Что сделано (ветка `feature/passed-fact` = `feature/check-keep-passed` + develop + `gate._log_before`).** К строке
  «Failed» по задетому удачному прогону добавлены три вызова лога перед местом расхождения, выводом
  `tests/runs.py steps`: «The log of run 8 before that call (\`python3 tests/runs.py steps 8 7-9\`): 7 @43 page_index = 0 →
  Output: Execution failed. Traceback… / 8 @46 … / 9 @49 page_index = 0 → Output: 17». Толкований нет. Сверено без
  модели одной синтетической правкой.
- **Гипотеза.** Увидев в ответе проверки, что в удачном прогоне тот же код сначала упал, а потом прошёл, писатель
  следующей правкой отделит такой повтор от цикла.
- **Мерка.** Развилка на ходу 25 сессии `t1_plain27t_s1` (ответ проверки на первую правку только что получен; bash
  осталось 2), `probes/1112/pf_roll.sh`, по 10 ответов на плечо, до ответа проверки на следующую правку. Считаю
  `probes/1112/fork_edits.py`: следующая правка меняет run 1 и не меняет удачные / задевает удачные / не действует.
- **Ожидание (записано до запуска, 10:09 по `date`).** base: чисто 1–3 из 10. pf: не меньше 5 из 10. Не сбылось, если pf
  не больше base + 2 (тогда урок TH переносится на 27B).
