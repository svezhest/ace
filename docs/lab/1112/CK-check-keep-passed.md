# CK — блок Check: удачные прогоны, не названные тикетом, по умолчанию должны идти как в логе

[Указатель проб](../INDEX.md) · хронология: [12.11](../days/1112.md) · повод: [P27](../1111/P27-base-27b-plain.md), [ST4](../1111/ST4-reference-agent.md)

- **Повод.** Блок «Check against the observation» судит только прогоны, названные в тикете. На № 1 (27B NT, T=0,6) он
  ответил «Ok» при двух задетых удачных прогонах (8 и 20) — писатель посмотрел run 8 и оставил правку. На 01, где в
  тикете есть keep, блок ответил «Failed» по run 8 — та же ступень сузила правку без bash. У эталонного агента на 06
  то же: «Ok» при 15 задетых из 24 ([ST4](../1111/ST4-reference-agent.md)). На № 4 писатель сменил промпт и добавил
  хук: сводка после смены промпта ничего не сравнивает, и задетый хуком удачный прогон 8 он увидеть не мог.
- **Слова автора (12.11).** «это норм в целом. просто помни что сравнивать можно только прогоны этого узла, т.е. именно
  этот харнесс». Отсюда условие в коде: прогон входит в проверку, только если на исходном `src/` вида он проигрывается
  без расхождений.
- **Что сделано (ветка `feature/check-keep-passed`, f92b7da, от develop d01e440).** `gate._passed_rest`: все удачные
  прогоны вида, не названные в `runs` и `keep` тикета; при правке текстов .md — код с текстами из вида; смена одного
  текста сообщения харнесса при том же поведении — «Ok» с оговоркой; до трёх строк «Failed: this edit changes run N,
  which passed and should still go exactly as in the log; …» и одна строка «Ok: the other K runs that passed still go
  exactly as in the log». `editor/rerun.py --json` отдаёт вид события расхождения.
- **Сверка без модели** (`editor/replay.py` на записанных сессиях `t1_plain27t_s1`, `t4_plain27t_s1`): № 1 — после обеих
  правок «Failed» по 8 и 20; № 4 — после хука «Failed: this edit changes run 8 … with the old texts it goes differently
  from model call 18 on». Раньше в обоих местах было только «Ok».
- **Гипотеза.** Писатель 27B NT сужает правку, когда блок Check называет задетый удачный прогон «Failed», и не сужает,
  когда тот же факт стоит только в сводке повтора.
- **Мерка.** Докаты настоящим харнессом (`editor/roll.py`) записанной сессии `t1_plain27t_s1` с хода 25 (сразу после
  ответа на первую правку), по три на плечо: база — код develop (ответ «Ok»), проба — код ветки (ответ «Failed» по 8 и
  20). Считаю докаты, где итоговый `src/` не задевает удачные прогоны и меняет run 1. Лимит bash прежний (25): в
  точке развилки осталось два вызова.
- **Ожидание (записано до запуска, 01:40 по `date`).** Проба: чисто не меньше чем в 2 из 3. База: 0–1 из 3. Не
  сбылось, если проба не лучше базы: тогда дело не в слове «Failed», а в том, что различитель не выводится.
- **Итог (докаты 02:51–03:42 по `date`; `probes/1112/ck_roll.sh t1 25 3`; логи `runs/ck_1112/logs/t1_{ck,base}_r{0,1,2}.jsonl`).**

  | плечо | докат | правок после первой | bash после первой | итог `src/` (провал / удачн) |
  |---|---|---|---|---|
  | проба (Failed по 8 и 20) | r0 | 5 | 2 | 3/2 — задевает 8 и 20; сдал при Failed |
  | проба | r1 | 6 | 2 | 3/2 — задевает 8 и 20; сдал при Failed |
  | проба | r2 | 3 | 2 | 2/0 — чисто |
  | база (Ok) | r0 | 0 | 2 | 3/2 (и run 3 — только текст) |
  | база | r1 | 0 | 2 | 3/2 (и run 3 — только текст) |
  | база | r2 | 1 | 1 | 2/0 (и run 3 — только текст) — чисто |

  - **Механизм включился:** после «Failed» писатель берётся сужать во всех трёх докатах (5, 6 и 3 правки), после «Ok»
    — в одном из трёх. **Итог не лучше:** чисто 1 из 3 в обоих плечах. Ожидание «не меньше 2 из 3» не сбылось.
  - Почему не сужается, по чтению. r0: верный замысел «тот же код и тот же вывод», но вывод сравнён с выводом
    соседнего шага чередования (`s.output == steps[-1].output`) — условие не истинно ни разу; строка Failed показала
    список `recent`, но не сказала, какая половина условия ложна, — писатель вернулся к широкому варианту; так дважды
    (мёртвое → широкое → мёртвое → широкое). r1: крутит одну ручку — размер окна 4 → 3 → 2 → 3; дважды печатал шаги
    run 8, оба раза только код, без выводов; сдал со словами «The guard now matches the observation exactly» — тикет
    действительно просит «look at the last few steps».
  - Удачные сужения (r2 здесь, `t1_bash-unnamed` в [BL](BL-bash-limit-anchor.md)) печатали шаги удачного прогона
    вместе с выводами и видели, что повтор там идёт после упавшего шага.
- **Вывод.** «Failed» по задетому удачному прогону заставляет пробовать, но различитель от этого не находится. Узкое
  место — вывести условие, отличающее законный повтор, и довести его до кода без ошибки на один индекс. Ветка не
  влита; решение — после пробы со строкой Failed для условия внутри `any(...)` ([FL](../1111/FL-failed-line-parts.md)
  мерилась при T=0, одна попытка).
- **Чего не пробовали.** Другие входы (№ 4, № 5); полные сессии на ветке; больше трёх докатов.
