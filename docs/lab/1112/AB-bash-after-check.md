# AB — bash после ответа проверки: есть чем разобрать «Failed»

[Указатель проб](../INDEX.md) · хронология: [12.11](../days/1112.md) · повод: [CK](CK-check-keep-passed.md), [BL](BL-bash-limit-anchor.md), [FA](FA-failed-line-any.md)

- **Повод.** Первая правка у 27B NT приходит на 22–36-м вызове bash при любом лимите ([BL](BL-bash-limit-anchor.md)), то
  есть при лимите 25 ответ проверки «Failed: this edit changes run 8…» писатель получает, когда разобрать его уже нечем:
  в докатах [CK](CK-check-keep-passed.md) и [FA](FA-failed-line-any.md) после развилки остаётся один вызов bash. При
  этом различитель «законный повтор против цикла» в рабочей копии виден готовым инструментом:
  `python3 tests/runs.py steps 8 6-11` печатает «7 @43 page_index = 0 → Output: Execution failed. Traceback…» и
  «9 @49 page_index = 0 → Output: 17». В BL большой лимит мерился без ответа «Failed» по задетым удачным (проверка
  отвечала «Ok»), а CK и FA — без bash. Вместе эти две правки не стояли.
- **Что сделано.** Ветка `feature/asm-1112` (e22e308) = `feature/failed-line-any` + `feature/bash-unnamed` (лимит
  bash 60, шагов 100, лимит писателю не назван). Нового кода нет.
- **Гипотеза.** С bash после ответа «Failed» писатель посмотрит шаги задетого удачного прогона и выведет различитель,
  а не будет крутить одну ручку.
- **Мерка.** Докаты `runs/ck_1112/logs/t1_ck_r0.jsonl` с хода 27, три штуки (`probes/1112/ab_roll.sh`), до 30 ходов.
  База — плечо `fa` пробы FA (та же развилка, тот же ответ проверки, лимит 25). Считаю: в скольких докатах после
  «Failed» есть вызов bash по удачному прогону; в скольких итоговый `src/` меняет run 1 и не задевает удачные.
- **Ожидание (записано до запуска, 04:16 по `date`).** bash по задетому прогону — в 2–3 из 3 (в записанном продолжении
  последний вызов ушёл именно на run 8 и 20). Чисто — 2 из 3. Сомнение: в BL на run 32 писатель сделал 18 правок
  подряд без единого bash при 30 оставшихся. Не сбылось, если чистых не больше, чем в базе.
- **Итог (докаты 05:50–09:25 по `date`, три с половиной часа на три доката; `probes/1112/ab_roll.sh 3`; разбор
  `probes/1112/rolls.py runs/ab_1112 27 t1_ab`).** Запрос на развилке сверен без модели: строки о лимите в промпте
  нет, сообщения о конце bash нет, строка со счётом по частям `any` есть.

  | докат | ходов | правок | bash после развилки | конец | итог `src/` |
  |---|---|---|---|---|---|
  | r0 | 25 | 23 | 1 | окно: HTTP 400, 57,6 тыс. токенов запроса | мёртвое: ни один прогон не меняется |
  | r1 | 20 | 14 | 5 | окно: HTTP 400, 57,9 тыс. | мёртвое: ни один прогон не меняется |
  | r2 | 21 | 9 | 11 (9 — по run 8 и 20) | finish | меняет run 1, удачные не задеты — чисто |

  База (плечо `fa` пробы [FA](FA-failed-line-any.md), 1 вызов bash): чисто 2 из 3.
  - **Ожидание не сбылось:** чисто 1 из 3 против 2 из 3 в базе. bash после «Failed» тратят все трое, но по-разному:
    r2 — девять вызовов на шаги run 8 и 20; r1 — три вызова подряд, потом правки; r0 — один вызов и 22 правки.
  - r0 — качели в чистом виде: 22 правки чередуют два состояния (мёртвое `s.output == steps[-1].output` ↔ широкое
    с `len({s.output …}) == 1`), строка со счётом по частям показана 11 раз.
  - r1 дошёл до различителя сильных моделей — `s.output.startswith("Execution failed")` (ход 29, ещё до bash), но
    приложил его к run 1, где повторяемые шаги не падают («`s.output.startswith('Execution failed')` was true for 0»):
    условие мёртвое. Дальше качели, потом переписал `run()` целиком с выносом шага в `_do_step`.
  - r2 — «Ok / Ok» на условии `code == recent[-3].code or (code == recent[-4].code and три вывода подряд равны)`: позиции
    подогнаны под проверку (как `>= 3` в FA r1), различителя нет.
  - **Найден брак прибора** (чинено в develop, 991e2f0). Последняя проверка r1 ответила «Ok: in run 1 the harness now
    acts differently: … from model call 1 on (the code run in the task differs)» на код, который не меняет ни одного
    прогона: условие `if not _do_step(episode, …)` проба значений вычисляла ещё раз, и код задачи исполнялся дважды.
    Теперь вызов функции `src/` по имени вычисляется, только если её тело без побочных эффектов; на том же коде
    проверка отвечает «Failed: this edit has no effect in run 1 … was true for 0». По всем 491 логам с проверкой тот
    же след («bridge, call 1») — ещё в одном: `runs/wvar_1104/02_TKP_s2` (6.11, серия и так с браком).
  - Потолок окна: при лимите шагов 100 правки без bash идут, пока запрос не перестанет помещаться (оценка `HARD_AT`
    54 тыс. не успевает: каждый ответ на правку — 3–4 тыс. знаков проверок).
- **Вывод.** Запас bash после ответа «Failed» не лечит — на 27B NT повторилось то, что [PKR](../1109/PKR-resume-bash.md)
  показала на 9B («keep Failed не чинит ни разу»). Три пробы подряд (CK, FA, AB) дают одно: после своей правки писатель
  либо качается между двумя вариантами, либо подгоняет ручку до «Ok», различитель после правки не выводится. Это урок
  TH из тикета («после своей правки данные толкуются в её пользу») и обратная сторона [K1c](../1110/K1c-with-run28.md)
  (удачный прогон перед глазами *до* замысла — 4–5 из 10 на 9B). Ветка `feature/asm-1112` не влита.
- **Чего не пробовали.** Другие развилки и входы; сообщение стенда «после этой правки `src/` тот же, что после правки
  N ходов назад» против качелей — набросал и проиграл r0 без модели: из 24 правок в точности прежнее состояние
  возвращает одна (ход 29), остальные «те же» условия отличаются текстом сообщения или соседним блоком, так что
  сообщение по отпечатку `src/` на качелях не сработало бы; ветку удалил; контраст во входе до первой правки — это [CI](CI-contrast-in-input.md).
