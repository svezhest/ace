## По входам

Ok — правка решает наблюдение и не ломает остальное; спорно — решает, но с изъяном, который не ясно, вредит ли;
F — не решает или ломает. В скобках — последний вердикт оценщика, если он расходится с разметкой.

| вход | bl s1 | bl s2 | ck s1 | ck s2 | cx s1 |
|---|---|---|---|---|---|
| 00 цикл из трёх | F | F | Ok (оц. F) | спорно (оц. F) | Ok |
| 01 A, B, A, B | F | F | F | Ok | Ok |
| 03 ложное «fail again» | F (оц. Ok) | Ok | F (оц. Ok) | Ok | Ok |
| 04 A, B, A, B в _is_new_step | Ok | Ok | Ok | Ok | Ok |
| 05 ответ из примера | Ok | Ok | Ok | Ok | спорно |
| 06 действие не из списка | Ok | Ok | Ok | F (оц. Ok) | Ok |
| 07 текст без вызова | Ok | Ok | Ok | Ok | Ok |
| 09 пример как сценарий | Ok | Ok | Ok | F (оц. Ok) | спорно |
| 14 «харнесс не видит» | F (оц. Ok) | спорно | F (оц. Ok) | спорно | F (оц. Ok) |
| t4 соединение двух API | спорно | Ok | Ok | Ok | Ok |

Почему так (только неочевидное):
- **00.** bl s1 ловит только одно и то же действие три раза — цикл из трёх не видит (оценщик: 0 прогонов иначе).
  bl s2: `all` → `any`, одно пустое действие из трёх кончает эпизод; цикл ловится с двух повторов и кончает удачный
  run 1 (там модель кружит pen 1 / pen 2 / inventory и выбирается). ck s1: периоды 1–3, действие и ответ среды равны,
  стоп; срабатывает в run 4 на take / take по кругу — run 4 и в логе кончился лимитом, круг настоящий, так что Failed
  оценщика («false positive… making progress») ложный; по нему писатель дочитал до 100 bash. Изъян мелкий: на 6 и 9–10
  шагах от начала возможен IndexError. ck s2: задумано «два предупреждения, потом стоп», но после предупреждения
  `continue` идёт до вызова модели — три сообщения подряд и стоп, предупреждений модель не видит; по действию — стоп на
  круге, как ck s1. cx s1: только период 3, три повтора — узко, но ровно по наблюдению, run 1 не трогает.
- **01.** `code == steps[-2].code` (bl s1, bl s2, ck s1) блокирует законный повтор после починки (run 2, шаг 26).
  ck s2 (A, B, A, B по коду) и cx s1 (A по коду, B по выводу) — нет.
- **03.** У шага в этом харнессе output не бывает None (None → конец эпизода). bl s1 и ck s1 ветвятся по `output is None`
  — ветка мертва, и повтор упавшего шага теперь получает «already ran successfully». Остальные ветвятся по
  «Execution failed» / «Traceback» — это верно (оба есть в выводе ошибки).
- **04.** Все пять пускают повтор после «Execution failed» и ловят A, B, A. Мелочи: bl s1 убрал проверку «тот же код, что
  на прошлом шаге», и повтор упавшего шага подряд больше не ловится; bl s2 и ck s2 убрали ветку рестарта (она по
  наблюдению сломана, точный повтор её покрывает в окне).
- **05.** cx s1 — блок по точной фразе примера плюс список вопросительных слов задачи («how many», «what»…); пример не
  тронут, задача «Tell me…» с ответом и той же фразой была бы заблокирована.
- **06.** ck s2: сообщение «No action was taken», но без `continue` — недопустимое действие всё равно уходит в среду.
- **09.** ck s2: заметка «the example above is finished… start your own task» вставлена в середину примера (перед
  выводом `23` и последним шагом с complete_task), две реплики USER подряд. cx s1: блок complete_task, если имя после
  `answer=` нигде не присвоено, — `answer=None`, `answer=len(x)`, `answer=True` тоже блокируются (в 30 записанных прогонах
  таких нет).
- **14.** Наблюдение — «харнесс не может проверить смысл, менять нечего» (как в EV15). ck s1 — одна строка «Do not repeat
  a step… calling an API you have already called» — не по наблюдению. bl s1 — 7 строк, из них 4 из других прогонов
  (play_count, точное совпадение поиска, «No API named», запуск плейлиста). cx s1 — советы в `on_init` (логин в один шаг,
  «никогда не повторяй шаг», проверка). bl s2, ck s2 — проверка состояния перед complete_task и «played so far» —
  ближе к делу, плюс по строке не по наблюдению.
- **t4.** bl s1 вставил в пример (диалог о плейлистах) новый ход с несуществующим `apis.app.show_related_item` —
  тот самый пример, который модель в 09 копирует дословно. Строка в B — верная.

## Итог

| серия | сессий | Ok | спорно | F | оценщик на итоге: пропуск / ложный Failed |
|---|---|---|---|---|---|
| база `bl_o4` | 20 | 12 | 2 | 6 | 2 / 0 |
| EV21 `ck_o4` | 20 | 13 | 2 | 5 | 4 / 1 (+1 спорно) |
| EV23 `cx_o4` (только s1) | 10 | 7 | 2 | 1 | 1 / 0 |
| для сравнения seed 1: база / EV21 / EV23 | 10 / 10 / 10 | 5 / 7 / 7 | 1 / 0 / 2 | 4 / 3 / 1 | |

- **Ожидание «Ok ≥ 10 из 20» сбылось** у EV21 (13) и у базы (12). Разница в одну правку — шум. На q5 (EV15): 10 / 3 / 6
  из 19; стенд другой, сравнение грубое.
- **Ожидание «медиана < 15» не сбылось:** первый check — медиана 27 bash (база 25, EV23 26).
- **Контекст > 50 тыс. — 8 сессий, все с check** (у базы 0): Ok 3 (00 ck s1, 06 ck s1, 09 ck s1), спорно 3 (00 ck s2,
  14 ck s2, 09 cx s1), F 2 (01 ck s1, 14 ck s1). Без названного лимита 27B читает дальше, но точнее от этого не становится.
- **Оценщик.** Все его Failed на итоге верны, кроме 00 ck s1 (ложный: «модель шла вперёд», а это настоящий круг в
  проваленном run 4) и 00 ck s2 (спорно). Пропуски: 03 (мёртвая ветка — перепрогон её не видит: повторов упавшего
  шага в логах нет), 06 ck s2 (действие уходит в среду, но перепрогон показывает только новое сообщение), 09 ck s2
  (промпт), 14 (×3). По оценщику Ok было 16 / 17 / 10 — по разметке на 3–4 меньше в каждой серии.
- **Что делает check.** Медиана — 1 check за сессию (первый же Ok кончает сессию). Failed → Ok по делу: 01 ck s2 (3 Failed за законный повтор, потом точная проверка A, B, A, B), 04 ck s1 (4 Failed),
  09 ck s1 (4 Failed: от подстрок примера к имени `num_playlists`). Застревания: 01 ck s1 (12 Failed подряд, ответы
  оценщика чередуются «0 runs go differently» / «blocks a legit retry», писатель мечется между двумя правками),
  00 ck s1 (ложные Failed).

## Что не пробовали

- Второй seed EV23 (без примера) — разница с EV21 7 против 7 на s1 не говорит ни о чём.
- Разметка EV24 (27B T) — серия на 00 шла, когда писалось.
- Проверить, был бы run 4 спасён, если бы круг не обрывал эпизод, а предупреждал (цикл с выходом — run 1 показывает,
  что модель иногда выбирается сама).
- Оценщик и мёртвая ветка (03): перепрогон логов её не покажет никогда; нужен другой вход (код правки целиком
  оценщику и так дан — он не заметил).

- **Поправка (18.11, EV29).** 01 cx s1: Ok → F. Сообщение подставляет задачу из примера в промпте (`memory["task"]` —
  первая строка `Task:`), и в каждом прогоне модель получает чужую задачу. Нашёл Haiku в [EV29](../1118/EV29-author-layout-haiku.md),
  сверено по diff.
